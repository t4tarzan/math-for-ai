# Recce: ai-engineering-from-scratch → math-for-ai → Floci capstones (2026-11-25)

A survey of the source repo, our June build, and Floci, written to decide the next arc.
Nothing here has been built yet. All figures were counted from a fresh shallow clone of
`rohitg00/ai-engineering-from-scratch` (pushed 2026-11-18) and the live Floci README and docs.

**The goal, as stated by the operator.** All content comes from ai-engineering-from-scratch.
Our product is the wrapper: easy sign-up, AI help, gamification and a clear UI, with the lessons
leading smoothly into the capstones. Learners build each capstone inside **Floci**, a local AWS
emulator, using Lambda, S3, the AWS CLI and the other services, and then host the result.

## 2. Our June build (math-for-ai), honestly

**Good, keep it:** a Next.js app shell, a lesson player, Pyodide code runner, XP, streaks and badges,
quest lines, hidden tests, progress sync API, Postgres, a waitlist, deploy-provision stubs and design tokens.

**Thin, replace it:** all 502 lessons are one generated 6-step template
(motto → problem → concept → build → ship → complete).
- Only **4** lessons were written by hand.
- **62** build steps are placeholders (`def x(x): return x`).
- **6** lessons have a figure, and **0** have hints.
- None of the source's quizzes, practice problems, projects or full lesson text is used.

**Verdict:** keep the app and the game layer, and throw away the generated lesson content.
Read the source's files directly instead.

## 3. Floci: what it is and how well it fits

`floci-io/floci` (MIT, ~32k stars, Java, pushed today) is a free drop-in replacement for LocalStack.
- One endpoint `http://localhost:4566`, with the real AWS CLI, SDKs, Terraform and CDK.
- A web console at `/_floci/ui`.
- Sibling emulators for Azure, GCP and OCI.
- hub2 already runs it inside hub4 DKubeX (the dclawstack/Foundry work).

**Services the capstones need, and how real each one is in Floci:**

| Need | Floci service | How real |
|---|---|---|
| Functions | Lambda (+ Function URLs, image-backed via ECR) | **real Docker** |
| Storage / static hosting | S3 (versioning, presigned URLs, events) · CloudFront | in-process |
| Vector search for RAG | **S3 Vectors** (cosine) · OpenSearch | in-process · real Docker |
| Databases | DynamoDB (+ Streams→Lambda) · RDS Postgres · ElastiCache | in-process · real Docker |
| APIs & auth | API Gateway REST/HTTP · Cognito · IAM/STS · Secrets Manager · KMS | in-process |
| Queues / events / workflows | SQS · SNS · EventBridge · **Step Functions** · Scheduler | in-process |
| Containers / clusters | ECS · EC2 · **EKS (real k3s)** · Batch · CodeBuild/CodePipeline | real Docker |
| Observability | CloudWatch Logs/Metrics · X-Ray | in-process |
| AI services | Textract · Transcribe · Comprehend · Rekognition · Translate · SageMaker | shape-level |
| **LLM calls** | **Bedrock Runtime `proxy` backend** → any OpenAI-compatible endpoint (Ollama, vLLM, OpenRouter) | **real model answers** for Converse and ConverseStream, including tool use. `InvokeModel` is still a stub. |

**The two real gaps:**
1. **GPU work** (fine-tuning, speculative decoding, distributed training) cannot happen inside Floci.
   SageMaker there is a control plane only, so GPU jobs must run on hub4/DGX or a rented box.
2. **"Host it"** inside Floci means a URL on localhost. A public URL needs either a real-AWS
   free-tier export (Terraform plan identical) or our own hosting lane (Vercel/dkube tunnel).

## 5. What this means for the product (input to the plan, not the plan)

1. **The content layer becomes a reader, not a generator.** Pin a source version and render
   `docs/en.md`, `quiz.json`, `practice/` and `projects/` as they are. Drop our generated lessons.
   A sync job pulls new source versions, and a diff shows what changed.
2. **Our value is four things the source site does not have:**
   - accounts with cross-device progress,
   - a real gamification layer,
   - an in-app AI tutor built on the source's own skills and MCP server,
   - the **Floci cloud lab** where capstones get built and hosted.
3. **The learning flow:** lesson (read, run code) → quiz → practice problem → project ladder
   (the source's 79 projects) → **Floci capstone** (deploy with the AWS CLI or Terraform,
   graded by an acceptance test that queries the emulator) → **Host it** (export to a public URL)
   → certificate and portfolio page.
4. **Each learner needs their own Floci, and that is the biggest open design choice:**
   - (a) **Bring your own:** `docker run floci/floci` on the learner's machine plus our CLI that grades it.
     Free and simple, but learners must install Docker.
   - (b) **Hosted sandbox:** one Floci per learner on hub4/DGX or rented VMs, with a web terminal
     and the Floci console in the browser. Smoothest for learners, but it costs compute and needs
     isolation work, since Floci's Lambda/ECS use the Docker socket.
   - (c) **Both:** hosted for the first capstone, bring-your-own after that.
5. **LLM calls inside the lab:** set Bedrock to `proxy` → our Ollama/vLLM gateway, so learners'
   Lambdas get real model answers with no AWS bill. Rate-limit each learner.
6. **The best first pilot is the RAG track (64–69 → capstone 08).** It is fully 🟢, uses the most
   AWS ideas a learner meets (S3, Lambda, API GW, S3 Vectors, Cognito, DynamoDB, Bedrock), and
   ends in a hostable chatbot. After that, 13 (MCP server) and 16 (issue-to-PR) are natural next steps.
